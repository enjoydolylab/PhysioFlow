# PhysioFlow 组会进展报告

**报告人：姜（JIANG）｜汇报范围：9/4 会议后至 2026/9/14**

本报告依据前次会议记录、9/8 补充记录及当前代码和验证记录整理。部分会议事项存在不同表述，列为待确认问题；不把讨论方案视为已完成实现。建议按以下七部分进行约 8–10 分钟汇报。

## 1. 本阶段目标与工作重点

**本阶段主要推进了实验自定义功能和 UI/UX，使研究人员更容易独立配置、编辑和检查实验。** 同时梳理了研究室局域网部署架构，为后续设备采集与数据库对接保留清晰边界。

会议中提出的问题包括：随机呈现与重复配置不方便、生理传感器同步存在困难，以及采集数据如何上传和保存。我的处理顺序是先完善能够独立推进的实验编辑环节；设备、数据库及处理平台的协同实现暂缓，先整理接口需求。

| 工作方向 | 当前状态 |
| --- | --- |
| 实验自定义、画布和属性编辑 | 已完成一轮实现与自动化回归 |
| 首页及运行前后的信息提示 | 已完成一轮整理 |
| 多语言支持 | 已建立初步审查工具，翻译补齐仍在进行 |
| 局域网系统架构 | 已整理目标结构与实施顺序，尚未完成实际部署验收 |
| 新版 DB 上传、真实设备同步、预处理平台 | 需要小组确认接口和分工后推进 |

## 2. 推进一：让实验自定义更接近研究人员的操作习惯

| 原先的操作问题 | 本阶段改进 | 对使用者的价值 |
| --- | --- | --- |
| 响应选项依赖文本格式，容易填错 | 将显示标签、记录值、快捷键改为逐项配置，并提示重复或空值 | 更容易看清“参与者看到什么、系统记录什么” |
| 认知任务的参数与已有试次关系不直观 | 增加明确的试次生成/替换入口，显示已保存数量与预览 | 修改参数不会悄悄覆盖已有试次 |
| 配置随机刺激需要寻找多个入口 | 在 Quick 模式中提供媒体库和刺激池入口 | 更容易完成素材上传、分组和抽样设置 |
| 重复一段实验流程需要手工连接循环 | 增加 Repeat a sequence，预览步骤与总遍数后建立循环 | 降低配置“刺激 → 响应，重复若干遍”的门槛 |

**目前的边界：**重复快捷入口适用于连续、单入口单出口的步骤，不自动包装复杂分支，也不会自动随机化步骤顺序。刺激抽样与流程重复是两项独立配置；目前尚未建立通用的条件表/Trial 系统。

这部分的设计想法是：先让常见实验能够用明确的表单与操作完成，再根据真实实验需求决定是否引入更复杂的模型。

## 3. 推进二：重整首页和可视化画布

首页已进行布局和入口整理，目标是缓解功能分散的问题。画布则围绕实际使用中出现的“空间太窄、拖动乱跳、只能自动排版、属性面板难找”等问题逐项改进。

| 改进 | 当前行为 |
| --- | --- |
| 保持画面比例 | 保存设计分辨率，编辑器与预览按原比例缩放；Fit 根据可用宽高适配 |
| 明确布局模式 | 自动布局中拖动用于排序；自由编辑中拖动用于移动坐标，切换模式可撤销 |
| 稳定选中和拖动 | Shift 点击增减选中，多选拖动后保持选择，Esc 取消当前拖动 |
| 整理属性面板 | 单选按位置尺寸、内容、外观和高级设置分组；多选显示批量操作 |
| 避免输入时跳动 | 坐标和尺寸在 Enter 或离开输入框后应用，Esc 放弃当前输入 |
| 减少误操作 | 锁定元素禁止编辑；文字仅在双击编辑后保存，修复切换焦点误改文字的问题 |
| 提供起点和检查入口 | 增加注视点、刺激、左右对比等模板，以及越界和缺失媒体提示 |

**已经验证的是交互行为，不是实验呈现精度。** 固定画面比例不能直接保证不同显示器上的物理刺激尺寸一致，浏览器测试也不能证明真实设备的时间同步精度。

### 建议现场演示：约 2 分钟

1. 打开一段“指导语 → 刺激 → 响应”的流程，展示重复配置和总遍数。
2. 打开参与者画布，选择设计分辨率，切换自由编辑。
3. Shift 多选两个元素并拖动，演示 Esc 取消。
4. 修改位置或尺寸，展示属性分组、提交输入和越界定位。
5. 打开预览，比较编辑画布与参与者画面的比例。

## 4. 推进三：可靠性、多语言和文档

**运行状态更清楚。** 准备页集中呈现实验模式、版本、资源和设备要求；运行过程中区分恢复检查点与服务器同步状态。最终保存结果与恢复快照清理结果分别处理，避免把一种操作成功误认为全部保存成功。

**多语言先建立审查入口。** 已增加文本候选扫描和审查文档，后续按中文、日文、英文逐项检查界面文案。实验作者输入的指导语、题目和变量名属于实验内容，应与系统界面翻译分开。当前扫描是启发式检查，不能据此宣称多语言已完整覆盖。

**文档按使用流程整理。** 更新了使用指南、开发说明、画布操作、局域网规划及实现状态，区分开发版新增功能与已发布安装包。

本轮验证记录：

- JavaScript 测试共 348 项：347 项通过、1 项跳过。
- 生产构建与 ESLint 零警告检查通过。
- 公开参与者浏览器回归通过，包含画布多选拖动、取消、锁定、属性提交和恢复相关检查。
- 文档本地链接与导航检查通过。

当前功能主要在本机开发环境中验证。研究人员独立操作、两台真实局域网工作站、Windows 系统缩放和真实设备仍需验证。9/14 的开发改动尚未重新打包成安装包。

## 5. 架构想法：局域网访问，采集与存储职责分开

目标是：**研究人员连接研究室内网后，用浏览器访问 PhysioFlow；设备由采集工作站接入，研究数据送入 BioDB/PhysioDB。**

```text
研究人员浏览器 ── 研究室内网 ── PhysioFlow 服务
  实验编辑、刺激呈现              协议、版本、资源、运行状态
  问卷、采集状态查看
          ↕ 待确定的本地接口
采集工作站：设备 → 本地采集服务 → 本地采集文件
                                      ↓ 上传器（待对接）
                                BioDB / PhysioDB
                           raw、processed 及相关元数据

独立处理应用：读取 raw → 执行前处理 → 保存 processed 与来源
```

这是目标职责划分，不表示图中链路均已实现。

- 设备驱动和采集保留在实际连接设备的电脑上；中央服务器不会直接控制其他电脑的 USB 或蓝牙设备。
- DB 负责数据保存；前处理、可视化及设备控制保持独立。已有 Hosted 服务可作为基础，但不等于新版 DB 或共享研究工作区已接通。
- 上传建议先完成“实验后上传 → DB 回读确认”的最小闭环，再评估实时上传。
- 界面需要明确区分“本地已保存、待上传、上传失败、DB 已确认”，避免用户误解数据状态。
- raw 与 processed 应保留来源关系，并记录处理程序版本和参数。程序如何管理、在哪里运行，等待小组决定。

“Python 多线程化”暂作为待分析的性能需求。获得实际脚本和耗时数据后，再判断线程、进程或独立计算资源是否合适。

## 6. 后续计划与验收方式

| 顺序 | 计划 | 完成判断 |
| --- | --- | --- |
| 1：可独立推进 | 用一个真实实验贯通“创建 → 配置 → 预览 → 运行 → 导出” | 研究人员无需改代码完成配置，能解释刺激顺序和导出结果 |
| 2：可独立推进 | 根据试用反馈继续完善模板、错误提示和主要页面多语言 | 中/日/英切换后主要任务可完成，无关键缺失或遮挡 |
| 3：先确认需求 | 评估条件表、试次组织和更完整的执行顺序预览 | 以小组真实实验说明重复、随机化、退出条件和记录归属 |
| 4：依赖设备/DB 接口 | 打通实验后上传最小闭环 | 一个会话的 raw、事件和问卷能上传并从 DB 回读核对 |
| 5：依赖部署资源 | 接入共享工作区、权限和持久化待上传队列 | 两台电脑可访问同一实验；断网、重启后数据可恢复且不重复 |
| 6：联合验收 | 真实设备、时间同步、备份恢复与研究人员试用 | 达到小组约定的精度、数据完整性及操作要求 |

计划按依赖关系推进，当前不承诺未经接口确认的完成日期。

### 可直接使用的结束发言

这段时间我主要把 PhysioFlow 的实验自定义和画布编辑做得更容易使用，并补充了运行状态提示、自动化检查和文档。局域网方向已经梳理，但新版数据库上传和真实设备同步还没有完成。下一步我会先用一个真实实验验证完整操作流程；同时希望小组确认实验与参与者的数据粒度、设备端与上传器的分工，以及同步精度要求，再推进集成。
