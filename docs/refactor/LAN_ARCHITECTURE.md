# 研究室局域网架构与实施顺序

更新：2026-09-12。目标：研究人员连接研究室内网，通过浏览器访问统一系统。本文区分现有实现与后续工作，不代表局域网部署已验收。

## 目标结构

依据用户提供的前次会议和 9/8 补充记录，目标调整为：浏览器访问 PhysioFlow 实验界面；采集工作站的本地服务接入设备、保留采集文件，经上传器将数据送入 BioDB/PhysioDB。两种 DB 名称是否为同一服务及实际 API 版本仍待确认。

会议提出的设备链路：OpenBCI → BrainFlow（Python）→ 本地服务；MyBeat → SDK → 本地服务。Web UI 查看设备信号，数据经上传器进入 DB。这是目标集成路径，不代表本仓库已完成或设备 SDK 已验收。设备面板的可视化职责不改变 PhysioFlow 的实验控制、刺激呈现和问卷职责。

设备连接在实际接入设备的采集工作站上；中央服务器不自动获得其他电脑的 USB 或蓝牙设备。需要原生驱动或 LSL 的设备可采用工作站采集代理，具体协议和同步精度须按设备验证。

- PhysioFlow 服务保存实验协议、冻结版本、刺激资源和运行恢复信息；BioDB 负责研究数据存储，并依据前次会议提供用户、项目及项目角色。先核对新版接口，不另建一套独立的研究室身份与权限体系。现有 Hosted 身份机制不是已完成的 BioDB 身份集成。
- 浏览器承担编辑与呈现，保留故障恢复副本。浏览器缓存成功与服务器持久化确认分别显示。
- 每次会话绑定协议版本、参与者和采集工作站。同一会话的并发控制、断网重传和冲突必须显式处理。
- 研究室单节点为首个目标，不引入多节点服务或实时多人共同编辑作为前置条件。

## 已有基础

- `server/hostedServer.mjs` 提供静态应用、Hosted API、健康检查和持久化状态。
- Hosted 发布、资源校验、参与者启动、事件批次及运行快照已有实现。
- `HostedRuntimeSync` 使用序号、批次标识和 revision 上传运行事件与快照。
- 公开参与者页可以使用服务器快照恢复，浏览器有较新本地快照时优先使用。
- 现有服务使用单进程 JSON 状态文件和独立资源目录，部署方式见 SELF_HOSTING.md。

## 本轮界面与可靠性改动

- 本地 Graph 准备页集中显示正式/测试模式、版本哈希、资源、设备要求与阻塞原因。
- 运行页显示检查点状态；服务器会话额外显示已确认运行事件数及同步失败重试。
- 本地最终保存与恢复快照清理结果分开；保留服务器会话的 hosted 来源标记。
- 本地会话复核显示运行模式、审核状态、跳过、重试和暂停；没有检查结果时不显示通过。

## 尚未实现的关键部分

1. **中央研究工作区**：当前本地项目列表和 SessionManager 不能当作全研究室共享工作区。优先核对 BioDB 登录、项目角色和实验接口，再接入共享草稿、版本发布与服务器会话复核；准备页依据实际存储后端判断要求。
2. **采集服务与上传器**：与设备实现负责人对齐本地服务接口，先打通实验后上传。当前 HostedRuntimeSync 不上传独立的 device_events 采样流。现有 bioDBClient.js 的 pushSessionToBioDB 可上传旧接口的传感器记录及可选通道字典，但不能视为新版 DB 完整上传器。需补齐原始文件、事件、问卷、设备元数据的关联与服务器确认，核对新版 API 后再实现分批上传与重复请求处理。
3. **断网恢复**：实现持久化待上传队列、重载后续传、服务器已确认位置对账及重复批次处理；明确网络中断时允许继续的范围。现有内存队列不是完整离线同步方案。
4. **会话所有权**：定义工作站标识、单个活动操作者及接管流程，处理两台电脑打开同一会话的冲突。
5. **存储演进**：按实际并发量和设备采样量测量 JSON 状态存储负载，再引入事务存储与独立采样文件；浏览器不直接连接数据库。
6. **运维与验收**：配置内网域名、HTTPS、服务器自动启动和独立备份；两台真实工作站验证权限、发布、采集、断网、服务重启和恢复。

## 接下来的交付顺序

先确认新版 DB API、设备本地服务及标识映射；再交付“采集完成 → 本地文件可核对 → 上传 → DB 回读验证”闭环和上传状态页；随后接入中央工作区与权限、持久化断网队列；最后验证真实设备和两台局域网工作站。实时上传作为后续能力，不替代实验后可靠上传的第一阶段验收。

## 会议事项的确定程度

- 明确方向：设备在客户端侧接入；实验数据上传 DB；DB 保存 raw 与 processed；处理逻辑与数据存储分离。
- 进行中：鍋島的 OpenBCI 集成；MyBeat 扩展仍需与负责人确认。不得依据会议中的“可能完成”标记为已实现。
- 待定：由姜负责上传器的任务分配、是否另建处理应用 DB、预处理程序的管理方式及执行资源。删除线内的逐处理容器方案不作为实施要求。
- 未解决：参与者是实验内独立还是跨项目共享；DB Experiment 与 PhysioFlow Protocol/Session 的粒度映射；BioDB 与 PhysioDB 的名称关系和 API 版本。9/8 记录没有明确消除前次纪要的冲突。
- “预处理 Python 多线程化”作为性能需求记录，待获得实际脚本和耗时分析后确定并发实现；本轮不选定线程、进程或分布式执行器。

## 接口与 UI 的下一轮具体交付

- DB 对接表：项目 ID、DB 分配的实验 ID、实验内参与者 ID、PhysioFlow 协议版本与会话 ID，分别记录而不相互替代。
- 本地采集接口草案：能力查询、设备配置、开始/停止、运行标记、采集状态、文件清单；与设备负责人实现核对后定稿。
- 上传清单草案：文件标识及校验和、设备/型号/通道/单位/采样率、电极或模式、时间来源、事件和问卷关联、实验者信息；processed 附原始数据引用及处理程序版本/参数。字段映射和大小限制以 DB API 为准。
- 上传 UI：本地已保存、待上传、上传中、失败可重试、DB 已确认分别显示；提供目标实验、文件数量和失败详情。只有服务端回执与回读验证满足契约后才标记完成。
- 处理应用先独立读取 raw、产生 processed 并登记来源。处理程序目录与 PhysioFlow 的协议存储是不同职责，不因都称“应用 DB”而合并。

正式验收必须核对：换电脑仍能看到已保存的实验与会话；服务器未确认的数据明确标为待同步；断网恢复不丢失、不重复；设备数据和运行事件可按会话及时间来源核对；备份可以在独立目录恢复。
